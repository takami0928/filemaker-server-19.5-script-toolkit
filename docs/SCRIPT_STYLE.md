# FileMakerスクリプト作法

## 1スクリプト1責任

画面制御、入力検証、業務処理、永続化、ログ、表示を一つの巨大スクリプトへ混在させない。ただし、数行の処理まで過剰に分割しない。

推奨区分:

- `UI | ...` クライアント上の画面制御
- `APP | ...` 業務ユースケース
- `SRV | ...` FMSEで実行する処理
- `SYS | ...` 共通技術処理
- `TEST | ...` テスト

## 入出力

単一値で明らかな場合を除き、スクリプト引数と結果はJSONにする。

入力例:

```json
{
  "requestId": "uuid",
  "recordId": "PR-000123",
  "options": {"dryRun": false}
}
```

結果例:

```json
{
  "ok": true,
  "code": "OK",
  "message": "",
  "data": {},
  "errors": [],
  "traceId": "uuid"
}
```

## 変数

- `$in`: 入力JSON
- `$out`: 結果JSON
- `$err`: 直前のFileMakerエラー
- `$context`: 実行コンテキスト
- `$recordId`: 対象主キー
- `$result`: サブスクリプト結果

`$$`グローバル変数は、セッション全体で本当に共有する状態に限定する。PSOSへ引き継がれると仮定しない。

## エラー処理

- サーバー処理では明示的に`Set Error Capture [ On ]`を置く。
- 失敗し得る重要ステップの直後で`Get ( LastError )`を保存する。
- エラー取得前に別のステップを挟まない。
- FileMakerエラー番号と業務エラーコードを分ける。
- すべての終了経路で同一構造の結果を返す。

## コンテキスト

フィールド参照、検索、レコード作成・更新の前に、処理用レイアウトへ明示的に移動する。レイアウト名と基準TOを仕様に含める。

## コメント

スクリプト冒頭に次を記載する。

- 目的
- 実行場所
- 入力
- 出力
- 前提レイアウトまたはコンテキスト再構築方法
- 副作用
- 呼出元

コメントは「何をしているか」より「なぜ必要か」を優先する。

## 単純さ

汎用ディスパッチャ、動的Evaluate、名前によるスクリプト実行は、静的参照で解けない理由が明確な場合に限定する。抽象化による行数削減より、追跡可能性を優先する。
