# サーバー実行設計

## 標準フロー

1. クライアント側で入力JSONを組み立てる。
2. `Perform Script on Server`を、必要に応じて「終了するまで待つ」で実行する。
3. サーバー側で入力JSONを検証する。
4. サーバー側の処理用レイアウトへ移動する。
5. 主キーで対象を再検索する。
6. 0件、1件、複数件を明示的に分岐する。
7. レコードロックを確認して更新する。
8. コミット結果を確認する。
9. ログとJSON結果を作成する。
10. クライアント側で結果を解釈し、表示だけを行う。

## PSOSを使う判断

適する例:

- 大量レコード処理でネットワーク往復を減らしたい
- サーバー上のODBC DSNやプラグインを使う
- クライアントを待たせずに独立処理したい

避ける例:

- ユーザーとの対話が必要
- 現在のポータル行や未確定入力に強く依存する
- 数件の単純更新で、PSOS開始コストの方が大きい
- サーバー非対応ステップが処理の中心

## 冪等性

再実行される可能性がある処理には、`requestId`、処理状態、処理済み日時等を用いて二重実行を防止する。

## レコードロック

- 編集開始・Set Field・Commitの各段階でエラーを確認する。
- ロック時に無限再試行しない。
- 再試行回数と待機戦略を仕様化する。
- ユーザーへ返す業務コードと、FileMakerエラー番号を分ける。

## 19.5での複数レコード更新

ネイティブな後続バージョンのトランザクション機能へ依存せず、事前検証、処理ID、作業テーブル、補償処理、バックアップ等を組み合わせる。これらは完全なACIDトランザクションの代替ではないため、リスクを明示する。
